# GitHub AI 小说工具对比与本项目优化建议

调研日期：2026-10-17（北京时间）。比较对象为当前工作区的 AI Novel Writer，`package.json` 版本为 1.0.6，Git 基线为 `b856bbd`。本报告是产品能力与代码结构分析，没有对竞品进行安装体验、同模型文笔盲测或长篇一致性跑分。

后续已补充 8 个项目的正文审核与字数控制源码核查，包含新加入的青春幻想引擎，详见 [审核与字数补充报告](E:/novel-ai-studio/docs/review-and-length-analysis-2026-10-17.md)。以下维护快照与原始核查深度保留为首次调研记录。

**建议的产品方向：面向中文长篇作者，把可追溯记忆、可控改稿和种田／成长类数值管理结合起来。** 当前已有较完整的功能链，下一步适合加强事实边界和作者操作体验。

## 研究依据与范围

- 直接检查 7 个主要候选的当前公开 README 和 GitHub 元数据，另查看一个 CLI 写作框架作为补充。星数、最后推送时间仅作日期快照，不用来推导文笔或稳定性。
- 当前项目检查了类型定义、上下文、混合检索与增量索引、剧情规划、局部修订、人物关系图、任务活动、数据库与导出实现。
- NovelWriter 额外检查上下文组装、摘要源指纹与过期判断；NovelForge 额外检查记忆失效、章节记忆和 token 预算代码。其他候选的功能主要以仓库文档为依据。
- DeepSeek 对明确选择的 5 个已跟踪源码文件做辅助盘点，Opus 对证据摘要和优先级做独立评审；最终建议经过主会话对照源码复核。外部模型没有读取私人稿件、数据库或密钥文件。
- 对第三方的“百万字一致性”“自动学习文风”“节省 50%–70%”等描述，仅作为设计线索，不认定为实测结果。部分旧搜索介绍与当前代码已不一致。

## 优先优化建议与验收方法

### 第一阶段：保证长篇记忆可靠

**1. 按目标章节组装事实，阻止未来正文和最新状态误入旧章。优先级 P0。**

现有前文摘要会按目标章过滤，但 [buildWritingContext](E:/novel-ai-studio/src/services/context.ts:294) 将全书语义记录交给检索；[持久检索](E:/novel-ai-studio/src/services/semanticIndex.ts:547) 的调用也未传目标章截止条件。角色、故事时钟和数据面板主要使用当前全局状态。这是代码层面可见的边界缺口，实际影响仍需合成故事回归验证。

建议建立统一的“本章事实视图”：事实带来源章节、来源正文版本、生效时间和确认状态；生成和审查使用同一视图。未来规划保留为作者意图，单独标注为计划，不能与已经发生的事件混用。历史状态没有证据时标记未知，避免用当前最新值补填。

后续可扩展“角色知道什么／读者已知什么／世界真实设定”的区别，服务悬疑和多视角叙事；先做可验证的章节边界，再推进完整知情模型。

验收：角色第 60 章死亡，改写第 20 章时不能用最新死亡状态判定冲突；第 50 章才揭示的真相，不进入第 20 章的已知事实区。作者允许参考的未来大纲仍保留在独立规划区。检索清单可解释每条资料为什么进入上下文。

**2. 对摘要、提取事实和聚合记忆补齐源版本与失效规则。优先级 P0。**

本项目已经有向量内容指纹与增量同步，不需要重做索引。需要补强的是派生资料与原正文的依赖关系：[章节编辑](E:/novel-ai-studio/src/stores/novel.ts:289) 可以更新正文，[章节摘要](E:/novel-ai-studio/src/types/novel.ts:347) 目前没有专门的来源正文修订字段；更新单个向量记录不能单独证明摘要和已提取事实仍有效。

给摘要、事实提取和卷级汇总记录来源修订号或内容指纹。正文变化后，只将受影响的派生资料标为待核查／待重建，查询时明确处理。已经确认的数据面板变更应进入核对流程，避免静默撤回作者确认的事实。

参考：[NovelWriter 的摘要源指纹与过期检查](https://github.com/Hurricane0698/novelwriter/blob/main/app/core/context_summaries.py)、[NovelForge 的受影响记忆收集与失效标记](https://github.com/LunaRime/novelforge/blob/3339a04af00bdca41d291958dab9bbaff1f5b70f/src/services/memory/memory-invalidation.ts)。这些实现可作为设计参考，不代表覆盖了本项目所有依赖场景。

验收：第 20 章的“药物 A”正式改成“药物 B”后，基于旧正文的摘要显示过期，并从可信事实区排除；重建后第 21 章能参考新事实。既有后续正文保持原样，界面列出可能需要作者复查的章节。

**3. 统一完整请求的输入与输出预算，并保留可解释记录。优先级 P0／P1。**

[当前上下文预算](E:/novel-ai-studio/src/services/context.ts:50) 主要使用字符长度与截取；[章节输出预算](E:/novel-ai-studio/src/services/chapterGeneration.ts:3) 已有独立控制，但需要在最终请求层合并检查。灵感对话已有上下文使用量，扩展时应覆盖正文生成、审查、摘要、提取等完整工作流。

最小技术改动是：计算或估算最终消息总量、预留输出空间、按重要度保留资料，并说明截取了什么。随后提供上下文检查器和调用账本，显示资料来源、估算输入、实际 usage、模型与失败次数。价格缺失时费用标未知；不同模型使用的估算口径要标清，不把统一 tokenizer 的结果称为所有模型的精确值。

[NovelForge 的预算实现](https://github.com/LunaRime/novelforge/blob/3339a04af00bdca41d291958dab9bbaff1f5b70f/src/services/agent/token-budget.ts) 有编码器、启发式估算和降级状态，可参考其可观测性。本项目 [AI 服务](E:/novel-ai-studio/src/services/ai.ts:55) 已返回 usage，适合在该边界归集；开发桥接工具的账本不能代替小说软件的产品内账本。

验收：小窗口模型收到长资料时，事实卡和当前任务优先保留；界面能解释被压缩或排除的资料。一次“生成→审查→修正”的子调用归到同一任务；未返回 usage、超时和价格未知均如实标注，不显示为免费或自动重复扣费请求。

### 第二阶段：让作者改稿更顺手

**4. 在现有局部修正上增加选区操作、逐项采纳与按需多候选。优先级 P1。**

已有局部修正基于审查意见生成替换块。建议复用其定位与过期保护，增加作者选中段落后的扩写、压缩、对白调整、增强冲突等操作；候选以原文与修改对照显示，每处可采纳／拒绝。需要比较方向时，作者主动选择生成 2–3 个候选，并可组合其中片段。

参考 [Arboris 的多候选设计](https://github.com/t59688/arboris-novel) 和 [NovelForge 文档中的段落操作](https://github.com/LunaRime/novelforge)。保留作者主笔模式的边界：只有作者显式发起并采纳的选区操作写入正文，不连带开启自动代写。

验收：只选择一段对白时，采纳候选仅影响该选区；模型生成期间原文发生变化则停止套用；未采纳候选不进入正式记忆，已锁定章节仍受保护。

**5. 把场景笔记逐步扩展为可执行的场景卡。优先级 P1，适合下一轮主要功能迭代。**

当前 `SceneNote` 主要保存标题与内容，写作顾问也有场景建议。可增加本场目标、冲突、视角角色、地点、参与者、剧情节拍、结束状态、相关伏笔和正文范围等字段，支持单个场景生成／修改，再组成章节。

先在现有章节内演进，保留整章写作入口和旧数据兼容。数组本身有顺序，不能仅凭缺少 `order` 字段断言现在无法排序；需要补的是场景任务、正文映射、版本与状态这一整套操作。

参考 [AI_NovelGenerator 的层级规划](https://github.com/YILING0013/AI_NovelGenerator/blob/main/README.zh-CN.md)。

验收：同章含三个场景，作者只重写第二场，第一、三场内容保持一致；场景顺序调整后重新核查人物出入场与事件依赖，不将旧笔记丢弃。

**6. 把文风设置发展为作者认可的样本与角色声音。优先级 P1／P2。**

现有 `WritingStyle` 已覆盖视角、基调、描写、对白、战斗、节奏与情绪，可以在此基础上保存作者主动认可的片段、修改前后示例、偏好／禁用表达，以及不同角色的说话特点。调用时按相关性注入少量样本，界面允许编辑、停用与回退。

参考 [GhostWriter 3000 的文风与系列记忆设计](https://github.com/zaphodsdad/GhostWriter3000) 和 [NovelForge 的角色声音描述](https://github.com/LunaRime/novelforge)。产品表达应是积累可编辑偏好；没有训练和效果验证时，不宣称已经训练出专属模型。

验收：同一场景用相同模型、相同事实分别生成有／无样本的候选，交作者盲选；观察语气、对白辨识与需要修改的字数，不能只用 AI 自评分证明文风更好。

### 第三阶段：根据实际使用推进性能与高级配置

**7. 做大书稿真实基准，再决定加载与存储优化。**

[数据库加载](E:/novel-ai-studio/src/services/db/novels.ts:100) 会读取章节正文与历史，[持久化](E:/novel-ai-studio/src/services/database.ts:139) 仍导出整库。已有 SQL 行级更新，下一步应测 100／500／1000 章、不同版本数量的启动、切章、编辑保存延迟和内存占用，然后决定按需加载、后台处理或存储边界调整。

验收使用合成资料与隔离数据库，给出同机器前后 p50／p95、数据规模和保存恢复结果。当前没有新的实测数字，不预先承诺倍数收益。

**8. 先做好默认创作流程与模板，再考虑节点画布。**

现有快速／均衡／严谨策略和写作 Skill 足以支撑清晰的默认路径。下一步可提供“研究资料→章计划→草稿→审核→确认事实”的可见进度、任务断点和模板复用。熟练用户出现明确需求后，再参考可编辑工作流加入节点画布。

多模型按任务质量与复杂度选择，普通任务只用必要步骤；难题可直接使用强模型。审查模型的自评分作为参考，稿件一致性与作者验收作为最终依据。

## 推荐实施顺序

| 顺序 | 可交付范围 | 作者能直接感受到的变化 |
| --- | --- | --- |
| A | 目标章节事实边界＋派生记忆版本绑定＋最小完整请求预算 | 改旧章时更少受到未来剧情、最新数值和旧摘要干扰 |
| B | 选区操作＋逐项采纳＋上下文／调用记录 | 看清 AI 看了哪些资料，方便只改自己想改的部分 |
| C | 场景卡与局部生成＋作者文风样本＋按需多稿 | 细化剧情控制，减少反复整章生成 |
| D | 大书稿基准后的性能优化＋高级模板／流程配置 | 随项目变大继续保持顺畅，熟练用户可调整流程 |

A 包含新状态模型和兼容迁移，应拆小步实现并先覆盖历史章节、角色状态、数值时间与稿件版本回归。完整角色知情体系可以在章节事实边界稳定后扩展，不以“加一个过滤参数”估算整个阶段的工作量。

## 后续怎样判断优化有效

准备一套合成小说样本：至少包含早期埋伏笔、后期揭晓、角色中途死亡、装备变化、故事时间推进、旧章改写，以及多视角知情差异。固定模型、上下文设置、目标字数和任务，保留请求资料清单与运行次数。

比较事实冲突数、来源可追溯比例、作者采纳率、实际修改字数、调用次数／usage、耗时，以及数据保存和恢复。创作性问题用作者或多名读者盲评，确定性数值和时态边界用测试校验。有限样本只说明该样本结果，不扩展成所有题材的绝对排名。

本轮产物为调研和优化方案；应用业务源码、版本号、安装包和公开自动更新配置保持原状。
