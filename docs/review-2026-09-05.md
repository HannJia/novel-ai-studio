## 审查总结

使用场景是作者自用或向少数朋友单独分享。当前功能结构足以支持此场景，优先级应是“书稿不丢、状态可信、错误可恢复”，不是增加账号、云服务器、多租户或复杂权限系统。

本轮完成全项目模块巡检、核心保存/导入/AI 请求链路深入检查、现有测试执行、依赖审计，以及本地隔离浏览器回归。不是对所有源代码逐行的形式化证明，也不是所有真实模型/文件格式的穷尽验收。`.compare` 参考项目、依赖与生成产物不作为产品源码审查。

## 初始关键问题（已在后续优化修复）

### R1 · P1：公式字段被页面安全策略阻断，错误静默保留旧值

- 位置：`src/services/dataPanel.ts:93`；`index.html:6`；`src/views/workspace/DataPanelWorkspace.vue:281`。
- 公式用 `Function(...)` 执行，而页面 CSP 只有 `wasm-unsafe-eval`，没有允许 JavaScript 动态求值。异常又被 catch 吞掉，作者看不到公式失败。
- 浏览器复现：隔离测试书创建“总周期=10、已成长=3、剩余天数=99、公式=总周期-已成长”。保存后仍显示 **99 天**，而非 7 天。
- 建议：实现受限的四则运算解析器，检测未知字段、循环依赖、除零并提示。不要为了公式添加 `unsafe-eval` 放松 CSP。补真实浏览器回归，Node 单测不足以捕捉此问题。

### R2 · P1：单独绑定/解绑知识库可能在重启后丢失

- 位置：`src/stores/novel.ts:680`、`:688`；自动保存判断位于 `:216`。
- 两个函数只修改 `knowledgeBaseIds`，没有更新小说 `updatedAt` 或标记 dirty。自动保存和关闭 flush 都依赖时间戳变化。
- 隔离测试已复现：保存一本书后仅绑定知识库，推进防抖计时，没有调用数据库保存。
- 建议：所有小说变更统一使用显式 dirty 标记；至少为这两个操作更新版本/时间戳，并测试绑定与解绑重载。

### R3 · P1：“立即保存”可能在最新修改尚未落盘时返回成功

- 位置：`src/stores/novel.ts:136`、`:189`；编辑器在 `src/views/workspace/ChapterEditor.vue:1248` 后把内容标记为已保存。
- 有旧写入正在执行时 `flushDirtyNovels()` 直接返回旧 Promise。此时第二次 `saveNovelNow()` 会等到旧快照保存完成就返回，新修改留待后续定时器处理。
- 隔离测试已复现：第一笔保存阻塞时改标题并再次保存，两次 Promise 均完成后数据库仍只收到旧标题。
- 建议：使用单调递增的修订号；`saveNovelNow(id)` 等待该次调用看到的修订号真正落盘。不要仅靠毫秒时间戳认定保存完成。

### R4 · P1：备份校验过浅，覆盖导入缺少全项目原子回滚

- 位置：`src/services/projectBackup.ts:22`；`src/stores/novel.ts:467`；`src/stores/knowledge.ts:82`；`src/views/NovelList.vue:268`。
- 只有 `id` 和 `chapters` 的小说能通过校验；缺 `entries` 的知识库也能通过。随后先清空旧数据，再逐项保存新数据，小说与知识库分两步导入。
- 隔离测试已证实残缺数据通过校验；按代码路径，后续读取缺失字段或写盘失败会产生部分导入状态，无法恢复为导入前完整项目。
- 建议：深层 schema 校验（数组、字段、ID 唯一性、关联引用、体积上限），先保存可恢复备份，再在单次数据库事务/新库中导入并校验，成功后替换。导入前应等待原保存队列排空。

## 初始其他风险与建议

### R5 · P1：数据库加载失败不应自动创建并保存空库

- 位置：`src/services/database.ts:28` 至 `:71`，`app-main/main.js` 的 `db:read` / `isSqliteFile`。
- 代码检查：主进程只检查 SQLite 头；若主库有合法头但内部损坏，渲染器加载异常后会走 localStorage/空库分支，再执行 schema 自动保存。已有 `.bak` 的完整性恢复也没有覆盖这种情况。
- 这项是明确的代码路径风险，本轮没有破坏真实数据库做实验。
- 建议：读取失败进入只读恢复界面，保留原文件，尝试经过 `integrity_check` 的备份；必须由作者确认后才能新建空库。

### R6 · P2：同一电脑多开软件可能互相覆盖数据库

- 位置：`app-main/main.js:74`、`:313`，以及统一的用户数据文件路径。
- 未见单实例锁。两个进程各自在内存里维护 SQLite，再导出覆盖同一个文件，串行保存仅限单进程，无法阻止跨进程旧快照覆盖。
- 建议：自用工具加 `requestSingleInstanceLock` 即可，第二次启动聚焦原窗口。暂不需要复杂的跨进程协作数据库。

### R7 · P2：默认本地向量服务地址与 CSP 不一致

- 位置：`src/stores/config.ts` 中默认 `http://127.0.0.1:11434`；`index.html:6`。
- `connect-src` 只额外允许 `http://localhost:5173`，不允许默认 Ollama 地址。即使本地服务正常，页面策略也会阻断请求。
- 建议：仅放行明确的回环服务，或通过严格校验目标地址的主进程桥接；不要全面允许任意 HTTP 地址。

### R8 · P2：2026-09-05 依赖审计有两项中危告警

- `@xmldom/xmldom@0.8.13`：生产链来自 `mammoth`（另有构建链引用）；XML 序列化相关告警。本轮没有证明当前 `extractRawText` 路径可触发漏洞，不能直接等同于“导入任意 DOCX 会被攻击”。
- `fflate@0.8.2`：来自 `@vitest/ui`，属于开发依赖；畸形 ZIP64 解析可能无限循环，不是本轮已证实的便携版正文风险。
- `npm audit`：0 高危、0 严重、2 中危；未修改依赖或锁文件。
- 建议：单独进行兼容修复升级与文件导入回归。分享给朋友时只提供干净发布包，避免携带源码调试依赖和个人数据目录。

### 可选优化：大书稿性能与模块化

- `ChapterEditor.vue` 约 3,347 行，`CreateWizard.vue` 约 1,432 行，小说 Store 约 1,300 行。继续按保存、定稿、后台分析和资料编辑职责逐步拆分，不做一次性“全重写”。
- 全量 deep watch + 全书 JSON 克隆 + 全章节 REPLACE + 整库 export 仍存在。5,000 条历史的测试不是百万字正文、多个历史快照的完整性能基准。
- 优先显式变更修订号、按书/章增量保存、按需加载正文；在这些瓶颈测量完成前不建议贸然更换数据库。
- 知识库文件导入应增加大小/页数/解压数量限制；EPUB 导入目前按文件名字典序，建议改为按 OPF spine 阅读顺序。
- Word 导出实际是 HTML `.doc`，界面已说明扩展名，但实现/注释仍称 Docx；可以后续统一命名或真正实现 DOCX。TXT/Word 默认包含大纲，给朋友试读时宜提供“只导出正文”选项。
- 增加项目保存错误的持久提示、损坏恢复指南、备份前后验证；比账号/云同步更符合当前使用场景。

## 本轮已修复的对话问题

- 添加真实搜索协议、按书开关、来源显示、能力不支持提示；关闭联网不添加搜索参数，并阻止已知联网专用模型假装关闭。

- 缺少 Key 时保留未发送输入并显示原因；失败信息不作为后续模型对话上下文；普通对话支持流式显示。
- 移除旧窗口中没有任何接收处理器的“应用建议”按钮，保留复制；不会误导作者以为内容已写入正文。
- 为对话窗口加入窄屏尺寸限制，390 × 844 回归无页面横向溢出。
- 按作者追加要求，灵感模式支持独立的联网开关，使用大纲模型；包含当前日期、现实/虚构分离和查询隐私提示。整理设定不重复搜索，安全来源有界保留到待确认表单；创建后随灵感历史保存。
